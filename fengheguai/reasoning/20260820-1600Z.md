## t0023 · explore · discard · val_bpb 0.973534

- **best after:** 0.973371

**Hypothesis (pre-registered).** The value-embedding path is the strongest mechanism in this recipe and it has never had its own learning rate. setup_optimizer already places value_embeds in a separate parameter group, but that group borrows embedding_lr from transformer.wte, so every rate experiment has moved both together. That makes t0014 uninterpretable in a specific way: raising the shared rate from 0.6 to 0.8 lost 0.000613, but the loss cannot be attributed, and wte is the likelier objector since it is a single bf16 table feeding a norm while the value embeddings are twelve tables injected into the attention value stream. The evidence that the mechanism is load-bearing has also grown, from 0.000902 at depth 8 to 0.001806 at depth 12 as measured by t0022. Decoupling the rates and giving the value embeddings 0.9 while wte stays at 0.6 should lower val_bpb.

**Change.** Optimizer change on champion t0017: setup_optimizer gains a value_embedding_lr argument that defaults to embedding_lr, so behaviour is unchanged when it is not supplied, and the existing value_embeds parameter group now uses it instead of embedding_lr. A new VALUE_EMBEDDING_LR constant is set to 0.9 and passed at the call site, while EMBEDDING_LR stays 0.6 for wte. No architecture, capacity, batching, masking or schedule changes: depth 12, width 512, document masking, dense value embeddings, batch 2**18, MATRIX_LR 0.0231, UNEMBEDDING_LR 0.002828 and WEIGHT_DECAY 0.2 all remain as in the champion.

**Predicted effect.** Expected decrease of roughly 0.0005-0.002 bpb versus champion t0017 at 0.973371 if the value embeddings were being held back by a rate chosen for wte. An increase would show that 0.6 was already right for both groups and that the t0014 loss came from the value embeddings rather than wte, which is equally informative because it would close the embedding-rate question that t0014 left genuinely open.

**Stated risk.** This adds a parameter group knob rather than a new mechanism, so the upside is bounded by how much the two groups actually disagree, and they may not disagree at all. The default-preserving signature means the change is inert unless the call site passes the new argument, which it does, so a null result would be a real null rather than a plumbing failure. A rate of 0.9 is also the highest any embedding group has run at here, and instability would appear as a much higher loss or a FAIL exit rather than a small regression.

## t0024 · explore · discard · val_bpb 0.982521

- **best after:** 0.973371

**Hypothesis (pre-registered).** This recipe has short skips and embedding skips but no long skips. Every layer already reads the token embedding through x0_lambdas, and every block has its residual path, but nothing carries mid-network representations forward: layer 11 cannot see what layer 0 computed except through eleven successive transformations. U-net style long skips address exactly this, pairing decoder layer i with encoder layer n_layer-1-i through a learned scalar, and they are a known win in the modded-nanogpt lineage this file descends from. At depth 12 the model is deep enough for the gap to matter, and depth is where this campaign found its largest gains, so giving the second half of the stack direct access to the first half should lower val_bpb.

**Change.** Architectural change on champion t0017: a new skip_lambdas parameter of length n_layer//2, zero-initialised, added to the optimizer as its own AdamW scalar group with the same settings as x0_lambdas. GPT.forward stores the output of each of the first 6 layers and adds skip_lambdas[i - 6] times the paired encoder output into the input of each of the last 6 layers, pairing layer 6 with 5 through layer 11 with 0. The parameter-count assertion, FLOP estimate and scaling-parameter report are updated to include the new scalars. Depth 12, width 512, document masking, dense value embeddings, batch 2**18, all learning rates, WEIGHT_DECAY 0.2 and every schedule are unchanged.

**Predicted effect.** Expected decrease of roughly 0.001-0.004 bpb versus champion t0017 at 0.973371. Zero initialisation means the network is mathematically identical to the champion at step 0 and can only depart from it if the optimizer finds the skips useful, so the mechanism has a floor near parity minus whatever the extra activations cost in steps. That floor is the main reason to prefer zero init over the ones init used upstream.

**Stated risk.** Holding six layer outputs alive across the stack extends activation lifetimes, so peak VRAM rises from the 66.8GB the champion used, and on a shared box that is the likeliest failure mode; it should cost a few percent of steps at most. The zero init is also a genuine design choice with a downside: if the useful skip scale is large, the scalar group may not travel far enough within 300 seconds to show the mechanism working, so a null result would be ambiguous between the mechanism not helping and the init being too conservative.

## t0025 · explore · discard · val_bpb 0.974106

- **best after:** 0.973371

**Hypothesis (pre-registered).** t0024 did not test the U-net skip mechanism; it tested a mis-parameterised version of it. The evidence is unambiguous: steps were 1465 against the champion 1470 and peak VRAM was 66795.3MB against 66795.6MB, so the skips cost no compute and the entire 0.009150 regression was a quality effect. The cause is the optimizer group I chose. This recipe treats its two scalar groups very differently, giving x0_lambdas the full scalar_lr of 0.5 and resid_lambdas only scalar_lr times 0.01, or 0.005. I gave a zero-initialised parameter the aggressive 0.5 rate, and because Adam normalises its step, a scalar starting at zero moves roughly 0.5 per step and reaches a magnitude of order ten within a hundred steps, which corrupts the residual stream it is added into. Rerunning the identical mechanism at the conservative 0.005 rate used for resid_lambdas should let the skips settle at a useful scale and lower val_bpb.

**Change.** Same architectural change as t0024, with one difference: the skip_lambdas AdamW group now uses lr = scalar_lr * 0.01, matching how resid_lambdas is treated, instead of the full scalar_lr that x0_lambdas gets. A zero-initialised skip_lambdas of length n_layer//2 is added, GPT.forward stores the first 6 layer outputs and adds skip_lambdas[i-6] times the paired encoder output into each of the last 6 layers, and the parameter-count assertion, FLOP estimate and scaling report are updated. Depth 12, width 512, document masking, dense value embeddings, batch 2**18, all learning rates, WEIGHT_DECAY 0.2 and every schedule are unchanged from champion t0017.

**Predicted effect.** Expected between a 0.003 decrease and parity versus champion t0017 at 0.973371. Zero init plus a slow rate means the mechanism is now genuinely floored near the champion, because the skips can only depart from zero as fast as 0.005 per step, so the downside is small and bounded. Over 1470 steps that still permits a displacement of several units if the gradient consistently favours the skips, so the rate is conservative without being inert.

**Stated risk.** The obvious objection is that this repeats a coordinate that just lost badly, and the defence has to be the diagnosis rather than the intent: identical step count and identical peak VRAM rule out throughput and memory, leaving the scalar rate as the only thing that differs between a mechanism that should be inert at initialisation and one that cost 0.009150. If this node also regresses, the mechanism itself is wrong for this architecture, not its parameterisation, and the U-net direction should be abandoned rather than tuned a third time.
