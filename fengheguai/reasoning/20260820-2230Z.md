## t0058 · explore · timeout · val_bpb —

- **best after:** 0.971630

**Hypothesis (pre-registered).** Every axis this campaign has probed is now closed except kernel selection, and the model runs at about 41 percent MFU with unusually small GEMMs: a 512-wide residual stream, a 2048-wide MLP and an 8192-row vocabulary. Those shapes are exactly where the default inductor heuristics are least likely to pick the best tile and stage configuration, and where autotuning has the most to recover. The decisive structural fact is that compilation happens lazily on the first forward pass, and the training loop only accumulates total_training_time for steps beyond the tenth, so autotuning cost lands in wall clock rather than in the 300-second budget. If autotuning finds better kernels, every step after the tenth is faster and the step count rises at identical quality per step, which converts directly into lower val_bpb.

**Change.** One argument added on champion t0053: torch.compile now uses mode max-autotune-no-cudagraphs instead of the default mode, with dynamic=False unchanged. The no-cudagraphs variant is chosen deliberately rather than plain max-autotune, because CUDA graph capture interacts badly with the document-mask path, which builds a cu_seqlens tensor of batch-varying length each step and is marked dynamic. No model, data, optimizer or schedule change accompanies this: batch 2**17, depth 12, width 512, document masking, dense value embeddings with the 128-channel gate, output softcap 10, rotary base 30000, all three settled learning rates, WEIGHT_DECAY 0.2, FINAL_LR_FRAC 0.1 and WARMDOWN_RATIO 0.5 are exactly as in the champion.

**Predicted effect.** Expected between a 0.003 decrease and parity versus champion t0053 at 0.971630. This is a pure throughput bet, so the diagnostic is num_steps against the champion baseline of 2838: a five percent gain would be about 2980 steps and should be worth roughly 0.001 given how the batch halving converted extra steps into loss. Quality per step should be unchanged since autotuning selects among numerically equivalent kernels, so any measured difference beyond noise is attributable to step count alone.

**Stated risk.** The real risk is the wall clock rather than correctness. Recent runs take 442 to 486 seconds against a 660-second process timeout, leaving roughly 175 seconds of headroom, and autotuning benchmarks many candidate configurations per distinct GEMM shape at first compile. If that exceeds the headroom the node fails on timeout rather than regressing, which costs this trial and a debug node to revert. I judged that acceptable because the alternative is another low-leverage knob on an axis already bracketed, and because a timeout failure is unambiguous and cheap to diagnose. A secondary risk is that autotuning selects kernels that are faster in isolation but interact worse with the varlen attention path, which would show as a step count at or below 2838.
