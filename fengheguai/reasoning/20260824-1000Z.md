## t0441 · explore · discard · val_bpb 0.965565

- **best after:** 0.961216

**Hypothesis (pre-registered).** The MLP bracket is closed and it says something about where to look next. 3x costs +0.006633 of capacity while 5x gains only -0.002872 -- removing width hurts 2.3x more than adding it helps, so 4x is a genuine interior optimum and capacity is strongly convex. Width cannot be bought or sold profitably in either direction. What that leaves is capacity-free structure: changes that improve how information moves through the stack without adding parameters or FLOPs.

This model injects the embedding x0 into every layer through x0_lambdas, but has no layer-to-layer skips. Every deep layer can see the raw token, and none can see what the corresponding shallow layer computed. U-net skips pair layer i with layer n-1-i: the first half pushes its input, the second half adds it back through a learned scalar. Six scalars for a 12-layer stack.

The specific reason to expect it here rather than generically: the attention placement work showed this model depends on periodic global integration and is badly hurt by long stretches where information cannot move -- clustering the full-context layers cost +0.0031 and dissolving them cost +0.0028. A skip is another route for information to cross depth, and it is the only one this architecture does not already have. x0 injection provides a shortcut from the input; nothing provides a shortcut from mid-stack.

**Change.** Five coordinated edits. A new nn.Parameter skip_lambdas of length n_layer//2 = 6, zero-initialised so the model starts exactly at the champion; an explicit zero_() alongside the other scalar inits; a skip_params list, its own AdamW group matching x0's settings, and the extended completeness assert; and the forward loop, where the first half appends x to a stack and the second half pops its partner and adds it scaled.
The parameter-count assert in setup_optimizer is what makes this safe to attempt: a new parameter that is not grouped fails loudly at init rather than silently going untrained. I extended that assert rather than working around it. Compile mode also reverts to default, for the wall-clock reason established by t0434/t0435/t0436/t0438, at a known -0.00067 handicap.

**Predicted effect.** Zero-init means this cannot hurt through the mechanism itself at step 0; any harm arrives through optimisation or through throughput. The cost model says a full-width elementwise op per layer buys ~2.8% of steps, but this adds six adds across twelve layers, ~0.5 per layer, and under torch.compile the add sits immediately after the existing resid/x0 mul-add so it may fuse into that kernel and cost nothing. I therefore expect steps to fall by 0 to 1.5% beyond the 1.14% the compile revert forfeits, and I will read anything beyond that as the skips failing to fuse.
On the mechanism: -0.002 to +0.001. The handicap means raw must clear -0.0007 of mechanism to beat the champion, so a small win will read as a null and route to a re-buy with autotune rather than to closing the axis.

**Stated risk.** This is the most invasive edit of the session -- five coordinated changes across four regions of the file -- and its crash risk is correspondingly the highest. Three of the five are guarded by exact-string asserts, and the parameter-count assert catches the grouping error at init. What none of them catch is a semantic error in the pairing: skips is a stack, so pop() gives layer i its partner n-1-i, and if I have that backwards the model still runs and still trains, just wired to the wrong partner. I checked the arithmetic (i=6 pops the entry pushed at i=5, which is n-1-i for n=12) but a silently wrong pairing would look like a null result rather than a bug, and I would not be able to tell them apart from the score.
Second risk: zero-init makes the skip neutral at step 0, which is safe but also means a real effect needs the scalars to move meaningfully within 2800 steps. t0424 showed a learned scalar can simply return to its initialisation and produce an exact null -- and if that happens here, the honest reading is unresolved-below-floor, not 'skips do not help'.

## t0442 · explore · discard · val_bpb 0.968566

- **best after:** 0.961216

**Hypothesis (pre-registered).** Disambiguate a confound I introduced. t0440 replaced the ReLU^2 MLP with parameter-matched SwiGLU and scored 1.044606 -- worse than the campaign's original baseline of 0.991068, which is the signature of something broken rather than something merely suboptimal.

The cause is an omission in my edit, not a property of SwiGLU. This model does not use PyTorch default initialisation: init_weights explicitly sets block.mlp.c_fc to uniform +/- sqrt(3)/sqrt(n_embd) and zero-initialises block.mlp.c_proj, alongside similarly hand-chosen scales for every attention matrix, the value embeddings at RMS parity, and gate weights at zero for neutrality. My c_gate was never added to that list, so it silently kept the default nn.Linear init at a different scale from everything around it. I flagged exactly this risk when queueing t0440 -- that SwiGLU changes initialisation scale implicitly and a bad interaction would show as a loss spike rather than a crash -- and then did not guard it. Naming a risk is not handling it.

This run adds the missing line so c_gate takes the same fan-in scale as c_fc, making the comparison actually about the functional form.

I want to be clear that the prior here is weak and this is primarily about not leaving a misleading result in the record. ReLU^2 is not a naive baseline -- it is what modern nanoGPT speedruns converge on -- and SwiGLU's usual advantage is measured against GELU. The reason to spend one slot is that t0440 currently reads as evidence against SwiGLU when it is evidence about an uninitialised matrix, and that distinction is worth one trial to establish.

**Change.** The t0440 edit plus one line: torch.nn.init.uniform_(block.mlp.c_gate.weight, -s, s) alongside the existing c_fc initialisation, using the model's own fan-in scale. MLP is gate/up/down SwiGLU at hidden 1344 (3*512*1344 = 2,064,384 params, -1.56% against ReLU^2's 2,097,152), c_proj still zero-initialised so the residual branch starts neutral exactly as before. Compile mode reverts to default for the wall-clock reason. Dry-run against champion source confirmed the init line lands inside the per-block loop.

**Predicted effect.** With initialisation corrected I expect a result in the normal range rather than a catastrophe: mechanism between -0.002 and +0.002. The handicap arithmetic is unchanged -- the compile revert forfeits about +0.00067, so mechanism must clear -0.0007 for raw to beat 0.961216.
The sharpest thing this can establish is negative: if the corrected version lands near zero, then t0440's +0.083 was entirely the missing init line, which is worth knowing because it calibrates how sensitive this model is to its hand-tuned initialisation -- every matrix in it has a chosen scale, and that suggests future structural edits adding any new matrix must extend init_weights or they measure noise.

**Stated risk.** The main risk is spending a slot to confirm a null. If corrected SwiGLU lands inside the floor, I learn that the functional form does not matter here, which is a real but modest finding.
A subtler risk: c_gate taking c_fc's scale is my assumption, not the model author's. The right scale for a gating matrix under silu is not obviously the same as for a value matrix under ReLU^2, so a poor result would still be partly confounded -- less severely than t0440, but not cleanly. I would not read a second bad result as closing the axis either; I would read it as this architecture being tightly co-designed with ReLU^2 and not worth further slots.
