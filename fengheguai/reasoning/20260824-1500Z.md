## t0480 · debug · timeout · val_bpb —

- **best after:** 0.961036

**Hypothesis (pre-registered).** Retry after a guard false positive -- the third distinct one this session, and the most instructive. The first attempt was aborted at 32.9% median MFU against a 34% floor while running normally: 21 layers at width 384 with 3 heads has intrinsically lower occupancy, because small GEMMs use the tensor cores poorly. That is the same effect §97 measured from the other side, where 8 layers at 640 ran FASTER than a FLOP count predicted.

A fixed MFU floor assumes every model reaches champion-like occupancy, exactly as the original fixed step-rate floor assumed every model has champion-like step cost. Checking the data before patching showed a within-run drop detector would not work either -- both genuinely contended runs were contended from step one and show 0.0% and 0.3% decline. The discriminator that does work is low MFU together with a co-tenant on our device.

The other side of the aspect-ratio bracket. The 8x640 arm trades four layers for 25% more width; this trades width for nine more layers: 21 layers at 384, depth*width^2 = 3096576 against the champion's 3145728, -1.6%.

Bracketing is what turned warmdown, MLP width and depth from apparent ramps into confirmed interior optima, and in each case a single arm would have suggested a direction and been wrong about the shape. The aspect ratio has never been varied independently at all, because DEPTH silently sets width -- so a one-sided result here would be especially easy to over-read.

The reachable points are sparse, which is worth stating: width must be a multiple of HEAD_DIM 128, so at roughly constant compute the only options are 12x512 (champion), 8x640, 21x384 and 5x768. There is no fine-grained scan available on this axis; three points is the whole bracket.

My expectation is that this loses badly. Depth measured 3.61x convex on removal one layer from 12, and while that says nothing directly about ADDING nine, the model's demonstrated appetite for depth was weak in that direction: depth 13 at constant width gained only -0.00167. Adding nine layers while cutting width to 384 -- below any width this model has run at except the old depth-8 trial -- combines a weak gain with a strong loss.

**Change.** DEPTH 12 -> 21 and ASPECT_RATIO 42 -> 18, giving 21 layers at width 384 with 3 heads. The edit asserts the champion's 12/42 and verifies the rounding before writing. Compile mode reverts to default since every GEMM shape changes. Dry-run verified against champion source.

**Predicted effect.** Steps should be roughly flat if depth*width^2 captures the cost, which is the same test the 8x640 arm applies from the other side -- and a useful cross-check on the cost model itself. If both arms hold steps within ~5% of the champion, depth*width^2 is a good compute proxy here; if either moves far more, it is not, and the 'constant compute' framing of both arms is wrong.
On the mechanism I expect a substantial loss, +0.004 or worse, for the reasons above. The value is the bracket: if BOTH arms lose, the champion's aspect ratio is a genuine interior optimum rather than the arbitrary 42 it looks like. If one wins, the ratio is mis-set and that is the largest structural finding available in this campaign.

**Stated risk.** Width 384 with 3 heads is a long way from anything the current champion has been tuned against -- every learning rate carries a 1/sqrt(model_dim) scaling that was calibrated at 768 and every schedule was shaped at 512. A bad result here is confounded with all of that, and I would not read it as 'depth is bad' so much as 'this model does not transfer to 384 wide'.
21 layers also changes the window pattern's long-layer count again (SSL over 21 layers), and with 3 heads the attention shape changes too. Like its partner arm this is the least clean kind of change, and both arms are worth running only because the question -- is the aspect ratio right? -- cannot be asked any other way in this config.
