## t0502 · recombine · failed · val_bpb —

- **best after:** 0.959724

**Hypothesis (pre-registered).** Throughput is the only axis still paying in this campaign, and all three of today's promotions came from it: max-autotune (+2.26% steps), the lm_head bf16 cast (+2.73%), and their combination (+5.05%, the current champion at 0.959724). Every capacity change measured today was real and unaffordable. So the question is what throughput is left.

The champion runs at ~111ms per step and 37-40% MFU. For a 12-layer model with a 512-wide residual stream, a large share of that gap to peak is kernel LAUNCH overhead rather than arithmetic -- many small kernels, each dispatched individually. CUDA graphs remove exactly that by replaying a captured graph. The compile mode stays max-autotune-no-cudagraphs so the tuned kernel SELECTION is preserved; this adds capture on top of it via torch._inductor.config.triton.cudagraphs.

I hold a memory that plain max-autotune segfaults through CUDA graphs -- but that is from the VPA campaign, on a different model and a different torch build. No node in these 502 trials has ever enabled them. That makes it a warning worth stating rather than a result, and this trial is what would turn it into one either way.

**Change.** Two lines after torch.set_float32_matmul_precision('high'): import torch._inductor.config and set triton.cudagraphs = True. The compile mode, the bf16 lm_head cast, the model, the data and every constant are the champion's, untouched. The edit asserts the champion's compile mode is present and that cudagraphs are not already enabled. Dry-run verified against t0500's source.

**Predicted effect.** Step count is the mechanism, as with every throughput bet here. If launch overhead is a real share of the 111ms step, I expect +3% to +10% of steps, worth -0.0017 to -0.0056. That range is wide because I am inferring the overhead share from MFU rather than measuring it -- the honest version is that I know graphs remove launch cost and do not know how much of this step is launch cost.
Read steps first. A neutral step count means launch overhead was not the bottleneck and the 40% MFU is arithmetic-bound after all, which is worth knowing on its own.
The registered failure mode is a hard crash or a segfault rather than a slow run, which is what the VPA memory describes. That would be fast, unambiguous, and would close the axis.

**Stated risk.** A segfault burns the coordinate, and I am knowingly testing something a memory warns against. I judge it worth one trial because the warning comes from a different campaign and torch build, because no node here has tried it in 502 trials, and because the payoff sits on the only axis that has produced a promotion all day.
The subtler risk is that CUDA graphs require static shapes and this model calls torch._dynamo.mark_dynamic on the varlen descriptor every step, precisely because the document count varies per batch. Graph capture and a genuinely dynamic input are in tension, and the most likely benign failure is that inductor silently declines to capture and the run is simply unchanged -- a null that means 'not applicable here' rather than 'launch overhead does not matter'. I would need to check the log for capture messages before drawing the stronger conclusion.

**Predicted effect.** Entirely determined by what the parent was, which this entry deliberately does not know. If the parent was a champion-parented no-op, this measures the champion again and should land within the observed same-source spread of 0.000195. If the parent carried an unmeasured experiment, this finally measures it and the relevant prediction is that experiment's, not this entry's.
Read the step count first as always. Because the configuration is inherited rather than chosen, I will identify what actually ran from the node's own config line before interpreting anything.

**Stated risk.** The real risk is that this entry is TOO general and starts absorbing requests that a targeted bet should have taken -- it sorts last precisely so it is only reached when everything else has refused. If it starts winning slots regularly, that is a signal the queue is stocked with champion-shaped bets while the engine is asking debug questions, and the fix is better queue composition rather than more fallbacks.
It also cannot distinguish a parent worth re-measuring from one that failed for a reason that will recur, so it may spend a slot repeating a configuration that dies the same way again. That is bounded: the ledger records each attempt, and a configuration that fails repeatedly under distinct hashes is itself informative.

## t0504 · explore · timeout · val_bpb —

- **best after:** 0.959724

**Hypothesis (pre-registered).** Throughput is the only axis that has paid in this campaign, and after four probes two are banked (autotune +2.26%, bf16 lm_head +2.73%, combining to the current champion) and two are closed (EXHAUSTIVE below the floor, CUDA graphs segfault). This is the next candidate and it comes from the same memory-traffic reasoning that made the bf16 cast work.

The logits tensor is 131072 x 8192 = 1.07 billion elements. In fp32 that is 4.29GB; in bf16, 2.15GB. `logits = logits.float()` reads the bf16 output of lm_head and writes the fp32 copy, and every downstream op then reads 4.29GB instead of 2.15GB. F.cross_entropy upcasts internally for its log_softmax, so this explicit materialisation is not what makes the loss numerically stable -- only the softcap tanh would move to bf16.

The reason this is worth testing NOW rather than earlier is specific. t0382 tested a bf16 softcap reorder and measured it exactly free, and I would have cited that as settling the question. But t0382 ran with an fp32 lm_head, where the conversion was fused into the matmul epilogue and cost nothing. The champion's lm_head has been bf16 only since t0484. The upcast is now a standalone conversion of the largest tensor in the model, which is a different situation from the one that measurement covered.

**Change.** One line removed: `logits = logits.float()`. The softcap tanh then runs in bf16 and F.cross_entropy receives bf16 logits, upcasting internally as it already does. No other change; the bf16 lm_head, max-autotune, model, data and constants are the champion's. The edit asserts the champion's bf16 lm_head is present -- this change only makes sense on top of it -- and that the logits path matches the expected three lines. Dry-run verified against t0500's source.

**Predicted effect.** Steps are the mechanism. If the upcast is a real standalone conversion, removing it saves 4.29GB written plus the difference on every subsequent read, and I would expect +1% to +4% of steps, worth -0.0006 to -0.0023. If inductor was already fusing the conversion into the matmul epilogue -- which is exactly what made t0382 free -- steps will not move and the answer is that the compiler had this covered.
Read steps first. A neutral result here is genuinely informative: it would mean the campaign's cost model ("count bytes at kernel boundaries, not at operations") is doing its job and I should stop proposing bandwidth savings the compiler already makes.

**Stated risk.** Numerical, and it is the real one. The softcap tanh now runs in bf16 on values that can reach +/-13 before capping, and bf16 has 8 mantissa bits, so tanh(logits/13) loses resolution near the flat regions of the curve. The loss itself should be fine -- cross_entropy upcasts -- but the GRADIENT through a bf16 tanh is coarser, and this sits directly on the output layer where every token's error signal passes.
If it costs quality, the signature is a mechanism residual clearly outside the floor with steps up, i.e. a genuine throughput-for-accuracy trade rather than a null. That is a legitimate result and I would not promote it even if raw improved, because a trade bought at the loss layer will not generalise to a longer budget the way a pure throughput win does.
